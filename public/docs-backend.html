Backend

Backend integration

Server-side integration covers API authentication, receiving webhook events, verifying webhook signatures, and using idempotency keys for safe retries.

Authentication

All Vouchflow API requests use Bearer token authentication. Pass your API key in the Authorization header:

HTTP
Authorization: Bearer vsk_live_••••••••••••••••••••••••••••

Key scopes

There are two key scopes:

ScopeUsed byAllowed endpoints
WriteMobile SDKPOST /v1/enroll, POST /v1/verify, POST /v1/verify/{id}/complete, POST /v1/verify/{id}/fallback
ReadYour serverGET /v1/device/{token}/reputation, GET /v1/verify/{id}

Keys are created and rotated in the dashboard under Settings → API Keys. Raw key values are shown exactly once on creation; the dashboard only stores a SHA-256 hash.

Key rotation

When you deprecate a key, the old key remains valid for 14 days. During this window, responses include the header:

HTTP response header
Vouchflow-Key-Deprecated: true

After the 14-day grace period, requests with the old key return 401 api_key_expired. Plan your SDK release cycle so users can update before the key expires.

Webhooks

Vouchflow sends a POST request to your endpoint after each verification completes. Webhooks are optional — you can poll GET /v1/verify/{id} instead — but recommended for real-time event handling.

Event types

EventFired when
verification.completePrimary verification finished (biometric path)
verification.fallback_completeEmail OTP fallback finished

verification.complete payload:

Webhook payload
{
  "event": "verification.complete",
  "session_id": "ses_01HZXK...",
  "verified": true,
  "confidence": "high",
  "context": "login",
  "timestamp": "2026-04-14T12:00:00Z",
  "api_version": "2026-04-01"
}

verification.fallback_complete payload:

Webhook payload
{
  "event": "verification.fallback_complete",
  "session_id": "ses_01HZXK...",
  "verified": true,
  "confidence": "low",
  "fallback_method": "email_otp",
  "fallback_reason": "biometric_failed",
  "context": "login",
  "timestamp": "2026-04-14T12:00:05Z",
  "api_version": "2026-04-01"
}
Device token is intentionally absent Webhook payloads do not include the device token. This limits exposure if your webhook endpoint is misconfigured. To correlate a session with a device, call GET /v1/verify/{session_id} and then look up the device token separately.

Delivery and retries

Vouchflow considers a delivery successful on any 2xx response. If your endpoint returns a non-2xx status or times out (10-second timeout), delivery is retried on an exponential backoff schedule:

AttemptDelay after previous
1Immediate
25 seconds
330 seconds
42 minutes
510 minutes
61 hour
76 hours
824 hours

After 8 failed attempts the event is marked webhook_failed and no further delivery is attempted. You can replay missed events by polling GET /v1/verify/{id}.

To test your webhook endpoint, use the test trigger from the dashboard or call GET /v1/webhook/test with your write-scoped key. The response includes the delivery status and the payload that was sent.

Every webhook request includes an X-Vouchflow-Signature header that you should verify before processing the payload. This prevents replay attacks and spoofed requests.

Signature format

Header example
X-Vouchflow-Signature: t=1744632000,v1=3d9f2c...
  • t — Unix timestamp (seconds) when the event was signed
  • v1 — HMAC-SHA256 hex digest of {t}.{raw_json_body}

Verifying signatures

JavaScript
const crypto = require('crypto');

function verifyWebhook(rawBody, header, secret) {
  const parts = Object.fromEntries(
    header.split(',').map(p => p.split('='))
  );
  const msg = `${parts.t}.${rawBody}`;
  const expected = crypto
    .createHmac('sha256', secret)
    .update(msg)
    .digest('hex');

  // Reject if signature doesn't match
  if (!crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(parts.v1)
  )) throw new Error('Invalid signature');

  // Reject if timestamp older than 5 minutes
  const age = Math.floor(Date.now() / 1000) - parseInt(parts.t);
  if (age > 300) throw new Error('Stale timestamp');
}
Python
import hmac, hashlib, time

def verify_webhook(raw_body: bytes, header: str, secret: str):
    parts = dict(p.split("=", 1) for p in header.split(","))
    msg = f"{parts['t']}.".encode() + raw_body
    expected = hmac.new(secret.encode(), msg, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, parts['v1']):
        raise ValueError("Invalid signature")
    if int(time.time()) - int(parts['t']) > 300:
        raise ValueError("Stale timestamp")
Go
import (
  "crypto/hmac"
  "crypto/sha256"
  "encoding/hex"
  "errors"
  "fmt"
  "strconv"
  "strings"
  "time"
)

func VerifyWebhook(body []byte, header, secret string) error {
  parts := parseHeader(header)
  msg := fmt.Sprintf("%s.%s", parts["t"], body)
  mac := hmac.New(sha256.New, []byte(secret))
  mac.Write([]byte(msg))
  expected := hex.EncodeToString(mac.Sum(nil))
  if !hmac.Equal([]byte(expected), []byte(parts["v1"])) {
    return errors.New("invalid signature")
  }
  ts, _ := strconv.ParseInt(parts["t"], 10, 64)
  if time.Now().Unix()-ts > 300 {
    return errors.New("stale timestamp")
  }
  return nil
}
Always verify before processing Parse the raw request body as bytes before JSON-parsing it. Any re-serialisation will change whitespace and break the HMAC. The 5-minute timestamp check prevents replay attacks even if a valid payload is intercepted.

Idempotency

The POST /v1/enroll endpoint supports idempotency keys to make enrollment safe to retry. If a request fails mid-flight (timeout, network error), resending with the same key returns the original response instead of creating a duplicate enrollment.

Idempotency key format

JSON field
{
  "idempotency_key": "ik_3f2a1b4c-5d6e-7f8a-9b0c-1d2e3f4a5b6c",
  // ... rest of enrollment request
}
  • Format: ik_ prefix followed by a lowercase UUID v4
  • TTL: 24 hours — after that, the same key is treated as a new request
  • The SDK generates idempotency keys automatically; you only need to set them if making direct API calls
  • If a request is in-flight and you send the same key again, you receive a 409 Conflict until the first request completes, then the cached response on subsequent calls
Public key uniqueness is independent Idempotency prevents duplicate enrollments for the same key, but the public key itself must also be unique. Attempting to enroll a different device with the same idempotency key returns the original response. Attempting to enroll the same public key with a different idempotency key returns 409 public_key_conflict.
