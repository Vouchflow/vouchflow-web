Integration guides

Practical patterns for common integration scenarios — from replacing SMS OTP to preparing for a production launch.

Replacing SMS OTP

SMS OTP is brittle: SIM-swap attacks, carrier delays, and international delivery failures all create real user friction and real security gaps. Device verification is a stronger signal because it's bound to hardware, not a phone number that can be transferred.

How they compare

SMS OTPVouchflow
What it provesPossession of a phone numberPresence on a specific physical device
SIM-swap resistantNoYes
Works offlineNoNo (challenge-response requires network)
User frictionHigh (wait for SMS, enter code)Low (biometric prompt, no typing)
Carrier dependencyYesNo
International costPer-SMS chargesPer-verification pricing

Migration strategy

A safe migration path that avoids breaking existing users:

  1. Deploy Vouchflow alongside SMS OTP
    Integrate the SDK and gate Vouchflow behind a feature flag. Run both paths in parallel — Vouchflow for users who pass, SMS OTP as fallback for those who don't. Measure conversion and confidence distribution before removing SMS.
  2. Retire SMS OTP for high-confidence users
    Once you have 30+ days of Vouchflow data, stop sending OTPs to users whose devices consistently return confidence: high. Keep SMS as fallback for medium and low confidence results.
  3. Remove SMS OTP entirely
    Replace the SMS fallback with Vouchflow's built-in email OTP fallback. Email OTP is included in your Vouchflow plan; you pay no additional per-message cost.

Signup flow integration

The most common integration point is at account creation. A device verification at signup gives you a baseline confidence score for the account before it ever logs in.

Where to call verify()

Call verify(context: .signup) early in your signup flow — ideally after the user enters their email but before they complete account creation. This gives you the signal before any account state is written.

Swift — signup flow
func createAccount(email: String, password: String) async throws {
  // 1. Verify device first
  let verification = try await Vouchflow.shared.verify(context: .signup)

  // 2. Pass the result to your server along with registration data
  let response = try await api.createAccount(
    email: email,
    password: password,
    deviceToken: verification.deviceToken,
    verificationSessionId: verification.sessionId
  )

  // 3. Your server can query device reputation before writing the account
}

Server-side validation

On your server, before creating the account, optionally query device reputation to make a risk-informed decision:

Node.js — server signup handler
async function handleSignup(req) {
  const { email, password, deviceToken } = req.body;

  // Query device reputation (read-scoped key)
  const reputation = await vouchflow.getDeviceReputation(deviceToken);

  if (reputation.riskScore > 80) {
    // High risk — require manual review or block
    return { status: 'review_required' };
  }

  if (reputation.anomalyFlags.includes('velocity_anomaly')) {
    // Device farm pattern — reject
    return { status: 'rejected' };
  }

  // Proceed with account creation
  await db.createUser({ email, password, deviceToken });
}

Handling low confidence

Low confidence doesn't mean the user is fraudulent — it means the device couldn't complete cryptographic verification. New devices, devices without biometrics, and devices that needed the email OTP fallback all return confidence: low.

Gating strategy

ConfidenceRecommended gate
highAllow without friction. Optionally skip 2FA for this session.
mediumAllow. Log for monitoring. Consider requiring 2FA for sensitive actions.
lowAllow for standard access. Require step-up (2FA, re-verification) for sensitive actions. Surface a message explaining why.
Communicate the reason If you restrict a feature based on confidence, tell the user why and what they can do about it. "This action requires verification from a trusted device. Please try again on your primary device, or complete the verification on this device." Users understand device trust; they do not understand opaque error messages.

UX patterns

  • Shadow mode — log low-confidence events for analysis without blocking users. Useful during rollout.
  • Soft block — allow the action but flag the account for review. Good for account creation where blocking new users carries high cost.
  • Hard block — require step-up verification before proceeding. Appropriate for fund transfers, password changes, and other sensitive actions.
  • Degraded experience — allow access but limit functionality (lower transfer limits, read-only mode, etc.) until confidence improves.

Going to production

Before switching from sandbox to production keys, work through this checklist.

Pre-launch checklist

  • ✓ App Attest entitlement set to production in release build (iOS)
  • ✓ Verified on a physical device — not just simulator
  • ✓ Certificate pinning configured (Android) with leaf and intermediate pins
  • ✓ Production API key set in release build; sandbox key in debug build
  • ✓ Webhook endpoint deployed, HTTPS, and signature verification implemented
  • ✓ Minimum confidence set appropriately for each sensitive action
  • ✓ Fallback flow tested end-to-end (biometric cancel → fallback → OTP entry)
  • ✓ Error handling for networkUnavailable and serverError — graceful degradation, not crash
  • ✓ Privacy policy updated to reflect device trust data collection

Certificate pinning (Android)

Provide both pins in your production VouchflowConfig. The leaf pin rotates with each Let's Encrypt renewal (approximately every 60 days); plan an app update cycle that stays ahead of each rotation.

Kotlin — production config
Vouchflow.configure(VouchflowConfig(
  apiKey                    = BuildConfig.VOUCHFLOW_API_KEY,
  environment               = VouchflowEnvironment.PRODUCTION,
  leafCertificatePin        = BuildConfig.VOUCHFLOW_LEAF_PIN,
  intermediateCertificatePin = "sha256/MbhbGJBPPfMVJDqwl..."  // ISRG Root X1
))
Rotate the leaf pin before expiry If you do not update the leaf pin before the certificate renews, production Android users will receive PinningFailure and be blocked from verifying. Monitor the Vouchflow-Key-Deprecated response header and the certificate expiry date from your dashboard.

GDPR compliance

Vouchflow processes minimal personal data and is designed to support your GDPR obligations. This section covers what data is processed, under what legal basis, and how to handle data subject requests.

Data processed by Vouchflow

DataPersonal?RetentionNotes
Device token (dvt_...)PseudonymousUntil deletionOpaque; no user identity on its own
Verification historyPseudonymous90 daysOutcome + timestamp only
Email address (fallback)PersonalNot storedDelivered to user then discarded
SHA-256 email hash (fallback)Pseudonymous24 hoursRate limiting only; cannot be reversed
IP addressPersonalNot storedIn-memory session check only

Legal basis

Vouchflow acts as a data processor on your behalf (you are the data controller). The legal basis for processing is typically legitimate interests (fraud prevention) or contract performance (authentication required to provide the service). Update your privacy policy to reflect device trust signal processing.

Handling deletion requests

When a user exercises their right to erasure:

  1. Call DELETE /v1/device/{device_token} with your read-scoped key. This permanently deletes the device record and all associated verification history.
  2. Delete the device token from your own database.
  3. The device will re-enroll as a brand-new device on next use, with no prior history.
Data Processing Agreement Vouchflow provides a standard DPA available from your dashboard under Settings → Account. Sign it before processing data from EU residents in production. Contact us if you need a custom DPA.
