Web SDK

Web SDK reference

The Web SDK wraps WebAuthn, IndexedDB-backed device state, and Vouchflow's verification protocol into a single async call. Adds high-assurance payload signing — a primitive the mobile SDKs don't expose. Modern evergreen browsers only; WebAuthn was added in 2018.

Web SDK — Private Beta Sandbox-only access; production GA targeted Phase 3 of the rollout. The package on npm is unlisted and the API key prefix must be vsk_sandbox_…. Contact us via /signup to request invite.

Installation

The SDK is distributed on npm as @vouchflow/web. Zero runtime dependencies. ESM and UMD builds ship in the same package.

npm
npm install @vouchflow/web

Or pull the UMD build via jsDelivr for prototypes and zero-bundler pages — Vouchflow attaches to window:

HTML — UMD bundle
<script src="https://cdn.jsdelivr.net/npm/@vouchflow/web/dist/umd/vouchflow.min.js"></script>
<script>
  window.Vouchflow.configure({ apiKey: 'vsk_sandbox_…', environment: 'sandbox', rpId: location.hostname, rpName: 'Example' })
</script>
React Applications using React can import from @vouchflow/web/react for the provider and hooks. The React entry point peer-depends on react@>=18 and only loads if you import it.

Initialisation

Call Vouchflow.configure({...}) once before any call to Vouchflow.shared. The SDK is safe to configure during module load — there are no async side effects until you call verify() or signPayload().

rpId is the #1 footgun rpId must equal the current origin's registrable domain or a subdomain. app.example.com works on app.example.com and example.com works on app.example.com, but example.com on app.acme.com fails with a SecurityError from the browser. The SDK surfaces this as invalid_config. If you change rpId after users have enrolled, every previously-enrolled credential becomes unusable — the SDK detects the mismatch and throws rather than letting WebAuthn fail opaquely.
TypeScript — module bootstrap
import { Vouchflow } from '@vouchflow/web'

Vouchflow.configure({
  apiKey:      'vsk_sandbox_••••••••••••••••',  // write key, not read key
  environment: 'sandbox',                       // 'production' in release builds
  rpId:        'app.example.com',              // registrable domain or subdomain
  rpName:      'Example',                      // shown in WebAuthn UI
})

VouchflowConfig parameters:

ParameterTypeRequiredDescription
apiKeystringYesWrite-scoped sandbox key (vsk_sandbox_) from Settings → API Keys. Production keys are not yet provisioned for web during the private beta.
environment'sandbox' | 'production'YesRequired, never inferred from the key prefix. Switching environments wipes local device state automatically so a sandbox device_token never gets posted to production.
rpIdstringYesWebAuthn relying party ID. Must equal the current origin's registrable domain or a subdomain.
rpNamestringYesDisplay name shown by the browser in the WebAuthn ceremony UI.
apiBaseUrlstringNoOverride the default https://api.vouchflow.dev. For self-hosted deployments only.
apiVersionstringNoVouchflow-API-Version header value. Defaults to a known-good date — leave unset unless pinned.

Enrollment

Enrollment is automatic on the first verify() call for a given userHandle. You do not need to call enroll() separately. The SDK:

  1. Calls navigator.credentials.create() with the configured rpId, asking for ES256 / RS256 / EdDSA, userVerification: 'required', and attestation: 'direct'
  2. Posts the attestation object (server extracts the public key) to POST /v1/enroll with platform: 'web'
  3. Stores the resulting device_token, credentialId, and attestation level in IndexedDB under the vouchflow database

Call enroll() explicitly only when you need to add a second credential (e.g. user wants to register a backup security key) or force a fresh credential:

TypeScript — explicit enrollment
await Vouchflow.shared.enroll({
  userHandle: 'user_abc123',
  forceNew:   true,                          // mint a new credential even if one exists
})
IndexedDB persistence Records survive across sessions and full browser restarts. In private / incognito mode IndexedDB is ephemeral, so the SDK treats every session as fresh enrollment. Switching environments (sandbox ↔ production) automatically wipes local state — a sandbox device_token will never get posted to production.

To check enrollment state without triggering a ceremony or biometric prompt, use getEnrollmentState():

TypeScript
const state = await Vouchflow.shared.getEnrollmentState({ userHandle: 'user_abc123' })
// state.enrolled        — boolean
// state.deviceId        — string | null
// state.credentialIds   — string[]
// state.lastVerifiedAt  — string | null  (ISO 8601)

To clear local records — for example, on sign-out:

TypeScript
await Vouchflow.shared.forget({ userHandle: 'user_abc123' })  // single user
await Vouchflow.shared.forgetAll()                              // every user on this device

forget() only clears local state. To revoke the credential server-side, call DELETE /v1/devices/:id from your backend.

Verification

Call Vouchflow.shared.verify({...}) wherever you need a device trust signal. The method is async, handles enrollment on first use, performs the WebAuthn ceremony, completes the session server-side, and returns a typed result.

TypeScript
import { Vouchflow, VouchflowError } from '@vouchflow/web'

try {
  const result = await Vouchflow.shared.verify({
    context:    'login',         // 'signup' · 'login' · 'sensitive_action' · custom
    userHandle: 'user_abc123',   // matches WebAuthn user.id; required for multi-user devices
    minConfidence: 'medium',    // default 'medium' for verify()
  })

  // result.verified      — true
  // result.confidence    — 'high' | 'medium' | 'low'
  // result.deviceToken   — pass to your server to query reputation
  // result.sessionId     — matches webhook session_id
  // result.biometricUsed — boolean
  // result.signals       — see VerifySignals below
  proceedWithLogin(result)

} catch (err) {
  if (err instanceof VouchflowError) handleError(err)
  else throw err
}

VerifyResult fields:

FieldTypeDescription
verifiedtrueLiteral true — failed verifications throw rather than returning verified: false.
confidence'high' | 'medium' | 'low'Combines attestation level, user-verification flag, and device history.
deviceTokenstringOpaque token for this device. Pass to your server to query GET /v1/device/:token/reputation.
sessionIdstringMatches the session_id in verification.complete webhooks.
biometricUsedbooleantrue when WebAuthn reported user verification (Touch ID, Windows Hello, etc.).
signals.keychainPersistentbooleantrue if the device record persisted across sessions (not a fresh IndexedDB).
signals.anomalyFlagsstring[]Active anomaly flags, if any.
signals.deviceAgeDaysnumberDays since first enrollment for this deviceToken.
signals.crossAppHistorybooleantrue if this device has verified in another Vouchflow-integrated app.
signals.attestationVerifiedbooleantrue if WebAuthn attestation validated server-side.

To require a minimum confidence — for example, on a sensitive action where you want hardware-attested only:

TypeScript — minimum confidence
const result = await Vouchflow.shared.verify({
  context:       'sensitive_action',
  userHandle:    'user_abc123',
  minConfidence: 'high',
})
// Throws VouchflowError({ code: 'minimum_confidence_unmet', actualConfidence }) if the device
// returns below 'high'. Catch and decide whether to block or degrade.

Payload signing

Web-only. signPayload() produces a Vouchflow-attested JWS over any JSON-serializable payload — useful for mandate signing, approval signing, or anywhere you need a single signed envelope your backend can verify with one library call.

The SDK canonicalizes the payload using RFC 8785 JCS before signing, so byte order doesn't depend on which engine produced the JSON. The default minConfidence is 'high' — signing is high-assurance by default.

TypeScript — signPayload
const signed = await Vouchflow.shared.signPayload({
  context:       'mandate_signing',         // arbitrary, audited per session
  payload:       { v: 1, id: 'mand_abc', scope: 'send' },
  userHandle:    'user_abc123',
  minConfidence: 'high',                    // default
})

// signed.payload         — canonicalized JSON string the user actually signed
// signed.assertion       — Vouchflow-signed JWS your backend verifies
// signed.signature       — raw WebAuthn signature, base64url (rarely needed)
// signed.algorithm       — 'ES256' | 'RS256' | 'EdDSA'
// signed.deviceToken     — same opaque token as verify()
// signed.signingDeviceId — sdv_… stable per-credential identifier
// signed.signedAt        — ISO 8601
// signed.confidence      — 'high' | 'medium' | 'low'
// signed.sessionId       — webhook session_id

await fetch('/api/mandates', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ mandate: signed.payload, assertion: signed.assertion }),
})

Server-side verification. The assertion is a JWS signed by Vouchflow's verifier key. Your backend verifies it with jose against Vouchflow's JWKS endpoint — no WebAuthn knowledge required:

TypeScript — Node.js backend
import { jwtVerify, createRemoteJWKSet } from 'jose'
import crypto from 'node:crypto'

const JWKS = createRemoteJWKSet(
  new URL('https://api.vouchflow.dev/.well-known/jwks.json'),
)

export async function verifyVouchflowAssertion(
  assertion: string,
  canonicalizedPayload: string,
  customerId: string,
) {
  const { payload } = await jwtVerify(assertion, JWKS, {
    issuer: 'https://vouchflow.dev',
    audience: customerId,
  })

  const expectedHash = crypto
    .createHash('sha256')
    .update(canonicalizedPayload, 'utf8')
    .digest('hex')

  if (payload.payload_sha256 !== expectedHash) {
    throw new Error('Payload hash mismatch — client sent different bytes than were signed')
  }

  return {
    confidence:      payload.confidence as 'high' | 'medium' | 'low',
    deviceToken:     payload.device_token as string,
    signingDeviceId: payload.signing_device_id as string,
    context:         payload.context as string,
    sessionId:       payload.session_id as string,
  }
}
Why a Vouchflow assertion, not the raw WebAuthn signature? Server-side WebAuthn verification is ~300 lines of fiddly attestation-statement parsing. The JWS bundle is one jwtVerify() call. Your backend trusts Vouchflow's signature; Vouchflow has already verified the WebAuthn signature, the user-verification flag, the origin, and the attestation chain.

Email fallback

When WebAuthn is unavailable, cancelled, or fails, request an email OTP fallback. The session ID returned in the thrown error feeds directly into requestFallback().

Email OTP is always low confidence completeFallback() returns confidence: 'low' — always, no exceptions. Email OTP proves the user controls an inbox; it does not prove a hardware-backed device is present. Customers using fallback must know they're not getting a hardware-attested verification. Block the sensitive operation, or downgrade the experience accordingly.
TypeScript — fallback flow
try {
  await Vouchflow.shared.verify({ context: 'signup', userHandle })
} catch (err) {
  if (
    err instanceof VouchflowError &&
    (err.code === 'biometric_cancelled' ||
     err.code === 'biometric_failed' ||
     err.code === 'webauthn_unavailable')
  ) {
    const fb = await Vouchflow.shared.requestFallback({
      sessionId: err.sessionId!,
      email:     'user@example.com',
      reason:    'biometric_failed',
    })
    // fb.fallbackSessionId, fb.expiresAt (ISO 8601), fb.codeLength === 6

    const code = await promptUserForCode()
    const completed = await Vouchflow.shared.completeFallback({
      sessionId: fb.fallbackSessionId,
      code,
    })
    // completed.verified === true · completed.confidence === 'low'
  }
}

FallbackReason is one of 'biometric_failed', 'webauthn_unavailable', 'user_chose_email'. The reason flows into the dashboard and webhook payloads so you can analyse why users took the fallback path.

Capability detection

Call checkSupport() before showing a passkey button — let users on browsers without a platform authenticator skip the WebAuthn prompt entirely.

TypeScript
const support = await Vouchflow.shared.checkSupport()

if (!support.webauthn) {
  showEmailOTPOnly()
} else if (!support.platformAuthenticator) {
  showSecurityKeyAndEmailOptions()
} else {
  showPasskeyButton()
}

CapabilitySupport fields:

FieldTypeDescription
webauthnbooleanwindow.PublicKeyCredential exists. False in Node / SSR.
platformAuthenticatorbooleanTouch ID / Face ID / Windows Hello / Android biometric available.
userVerifyingAuthenticatorbooleanSame value as platformAuthenticator on every shipping browser today.
conditionalUIbooleanPasskey-autofill UI available. (The SDK's verifyConditional() is v2-deferred — read the field for your own UI logic.)
attestation'available' | 'unsupported''available' when WebAuthn is here at all — attestation quality is checked server-side post-ceremony.
recommendedFallback'email' | 'none'Helper for the common case: 'email' when no platform authenticator, 'none' otherwise.

React hooks

The React entry point (@vouchflow/web/react) is a thin wrapper around the core. It exposes a provider, a singleton accessor, and stateful hooks for the two primary actions.

tsx — VouchflowProvider
import { VouchflowProvider } from '@vouchflow/web/react'

export function App() {
  return (
    <VouchflowProvider config={{
      apiKey:      'vsk_sandbox_…',
      environment: 'sandbox',
      rpId:        'app.example.com',
      rpName:      'Example',
    }}>
      <SignInButton />
    </VouchflowProvider>
  )
}

useVerify() wraps verify() with loading state and last-result tracking:

tsx — useVerify
import { useVerify } from '@vouchflow/web/react'

function SignInButton() {
  const { verify, isVerifying, lastResult, error } = useVerify()

  return (
    <button
      disabled={isVerifying}
      onClick={() => verify({ context: 'login', userHandle: 'user_abc' })}
    >
      {isVerifying ? 'Authenticating…' : 'Sign in with passkey'}
    </button>
  )
}

useSign() is the same shape for signPayload():

tsx — useSign
import { useSign } from '@vouchflow/web/react'

function MandateSigner({ mandate }: { mandate: unknown }) {
  const { sign, isSigning, signedResult, error } = useSign()

  const handle = async () => {
    const r = await sign({
      context:       'mandate_signing',
      payload:       mandate,
      userHandle:    'user_abc',
      minConfidence: 'high',
    })
    await fetch('/api/mandates', {
      method: 'POST',
      body: JSON.stringify({ mandate: r.payload, assertion: r.assertion }),
    })
  }

  return <button disabled={isSigning} onClick={handle}>Sign with passkey</button>
}

Hooks don't add behaviour beyond exposing loading state and the last result. Anything else stays in application code — call Vouchflow.shared.verify() directly when you need full control.

Error handling

All SDK errors are instances of VouchflowError. The class has a discriminated code field; switch on that, not instanceof per case.

TypeScript — full error handling
import { Vouchflow, VouchflowError } from '@vouchflow/web'

try {
  const result = await Vouchflow.shared.verify({ context: 'login', userHandle })
  proceed(result)

} catch (err) {
  if (!(err instanceof VouchflowError)) throw err

  switch (err.code) {
    case 'biometric_cancelled':
      return showRetryPrompt()

    case 'biometric_failed':
    case 'webauthn_unavailable':
      return offerEmailFallback(err.sessionId)

    case 'minimum_confidence_unmet':
      return handleLowConfidence(err.actualConfidence)

    case 'concurrent_ceremony':
      // Another tab is mid-verify; ask user to retry in this tab.
      return showActiveTabHint()

    case 'invalid_config':
      // Almost certainly an rpId mismatch with the current origin.
      return logBugAndShowGeneric(err)

    case 'network_error':
      return showOfflineState()

    default:
      logError(err)
      return showGenericError()
  }
}

CodeDescriptionRecommended action

not_configuredVouchflow.shared accessed before configure()Fix at init
not_in_browserverify() / signPayload() called outside a browser contextUse checkSupport() in SSR builds
webauthn_unavailableBrowser does not support WebAuthnOffer email fallback
platform_authenticator_unavailableNo Touch ID / Windows Hello / Android biometric presentOffer security-key or email fallback
biometric_cancelledUser dismissed the WebAuthn prompt, or the prompt timed outOffer retry; err.sessionId is set for fallback
biometric_failedCeremony completed but the server rejected the resultOffer fallback using err.sessionId
concurrent_ceremonyAnother tab on this origin is already mid-ceremonySurface a hint; WebAuthn is exclusive per origin
enrollment_failedServer rejected the enrollment attestationUsually transient; safe to retry
invalid_signatureWebAuthn signature did not validate server-sideLog; possible state corruption — clear and re-enroll
challenge_expiredChallenge was unused past the 60s windowRetry; SDK normally fires within ms

Browser support

The SDK targets evergreen browsers with WebAuthn + IndexedDB + Web Crypto. WebAuthn was added to the platform in 2018; IE and legacy Safari are out of scope.

BrowserMinimumNotes
Chrome109+Full WebAuthn + conditional UI
Edge109+Same engine as Chrome; same support
Safari16.4+iOS 16.4+ and macOS 13.3+ for full passkey support
Firefox119+WebAuthn support is mature; conditional UI lags Chromium
HTTPS or localhost required WebAuthn refuses to run over http:// on any host other than localhost. Make sure your staging and preview environments have valid TLS — preview deploys served from http://192.168.x.x will throw webauthn_unavailable the moment you call verify().

In Node.js, Server Components, or any non-browser runtime, verify() and signPayload() throw not_in_browser. checkSupport() returns capability flags false everywhere. The package is import-safe in SSR — only the active call sites need a real browser.

Confidence ceiling per attestation format

The server caps confidence at enrollment time based on the WebAuthn attestation format. The ceiling is per-device and never raised by later activity — only the realised confidence on each verification can sit at or below it.

Attestation formatCeilingTypical authenticators
applehighTouch ID / Face ID on macOS & iOS Safari
android-keyhighAndroid biometric with hardware-backed keystore
tpm (valid cert chain)highWindows Hello with TPM 2.0
packed (with attestation cert)highFIDO2 security keys (YubiKey, Feitian)
packed (self-attestation)mediumAuthenticators without a vendor attestation cert
android-safetynetmediumOlder Android devices using SafetyNet
nonemediumMost platform authenticators when the browser strips attestation
Software-only (e.g. 1Password)mediumRoaming passkeys with no attestation chain
Email OTP fallbacklowcompleteFallback() — never higher

The default minConfidence is 'medium' for verify() and 'high' for signPayload(). Raise the threshold when you need hardware-attested only; the SDK will surface minimum_confidence_unmet with the actual ceiling in err.actualConfidence so you can decide whether to block or degrade.
