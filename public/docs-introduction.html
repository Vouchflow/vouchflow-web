Introduction

Vouchflow verifies that a user is operating from a trusted, real device — without passwords, OTPs, or friction. It gives your backend a cryptographic signal it can act on.

What is Vouchflow?

Most authentication systems prove who a user is. Vouchflow proves what device they're on. A verification result tells your server that the request originated from a specific hardware-bound keypair on a physical device, that the device has passed platform attestation (Apple App Attest on iOS, Android Keystore Attestation on Android), and that the device has an observable history — age, prior verifications, network standing.

This lets you make risk decisions that credentials alone can't support: allow a login without a second factor from a high-confidence device, require step-up from a new or low-confidence one, reject requests from emulators or rooted devices entirely.

Not a replacement for identity Vouchflow is a signal layer on top of your existing auth, not a replacement for it. You still own the user identity. Vouchflow tells you how much to trust the device that identity is coming from.

Who it's for

Vouchflow is built for mobile-first products where device trust is a meaningful risk signal:

  • Fintech and payments — gate high-value transfers behind device verification instead of (or in addition to) OTP
  • Marketplaces — detect multi-accounting and bot signups that bypass traditional defences
  • Consumer apps — reduce fraud at signup without adding friction for real users
  • B2B SaaS — enforce device trust policies for sensitive admin actions

How it works

A Vouchflow verification is a three-step process: enroll the device once, then issue a signed challenge-response on every subsequent verification.

  1. Enrollment
    The SDK generates a hardware-bound EC keypair and registers the public key with Vouchflow. On iOS this uses the Secure Enclave; on Android it uses StrongBox or TEE. The SDK also submits a per-device attestation proof — an App Attest object (iOS) or Keystore Attestation cert chain (Android) — that proves the keypair lives in real hardware and was generated for this enrollment. The Vouchflow server validates the chain against Apple's or Google's public root CA and checks that your app's identity (team ID + bundle ID on iOS; package name + signing-cert digest on Android) matches what you registered. Enrollment is automatic: your code only calls verify(), and the SDK handles enrollment transparently on first call.
  2. Challenge
    Your app calls verify(). The SDK opens a session on the Vouchflow backend, which returns a 32-byte random challenge scoped to a 60-second window. The SDK signs the challenge with the device's private key and (if configured) presents a biometric prompt to prove the user is physically present.
  3. Verification
    The Vouchflow backend verifies the signature against the enrolled public key. It computes a confidence level based on attestation status, biometric usage, device age, and network standing. The result is returned to the SDK and optionally delivered to your backend via webhook.

Confidence levels

Every verification returns one of three confidence levels:

LevelMeaningTypical gate
highAttestation verified, biometric used, device has historyAllow without step-up
mediumNo attestation (e.g. simulator), or biometric not usedAllow with monitoring
lowFallback via email OTP; device could not complete primary pathRequire additional verification

You can set a minimumConfidence threshold on any verification call. If the device cannot meet the threshold, verify() throws MinimumConfidenceUnmet rather than returning a low-confidence result silently.

Physical device required in production App Attest (iOS) and Android Keystore Attestation only produce a verifiable chain on physical devices. On a simulator/emulator, attestation is either unavailable (iOS) or generates a software-only chain that doesn't root in Google's HW Attestation Root CA — confidence is capped at medium. This is expected in sandbox, but will affect users in production if you ship without testing on real hardware.
Register your app's identity in the dashboard Before going live, set your Android applicationId + signing-cert SHA-256 and iOS team ID + bundle ID in Settings → Account → App identity (attestation). The attestation chain proves a key was minted in real hardware, but it doesn't, by itself, prove which app requested that key — every chain carries the requesting app's package name + signing-cert digest (Android) or <TEAM_ID>.<BUNDLE_ID> (iOS) inside, and the server has to match that against values you've registered. Without them, an attacker who pulled an attested key out of any other Android/iOS app could submit it as if it came from yours. Until you register, all devices fall back to confidence_ceiling: medium.

API key scopes

There are two key scopes, and you use them in different contexts:

  • Write-scoped (vsk_...) — used by the mobile SDK. Allows enrollment, verification, and fallback. Never expose these in server-side code or web clients; they're embedded in the mobile app binary.
  • Read-scoped (vsk_...) — used server-side. Allows querying device reputation and session state. Keep these server-only.
