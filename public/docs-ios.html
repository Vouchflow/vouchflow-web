iOS SDK

iOS SDK reference

The iOS SDK wraps App Attest, Secure Enclave key management, and the Vouchflow verification protocol into a single async call. Requires iOS 15+, Xcode 15+, Swift 5.9+.

Installation

Add the package via Swift Package Manager. In Xcode, go to File → Add Package Dependencies and enter the repository URL, or add it directly to Package.swift:

Package.swift
dependencies: [
    .package(
        url: "https://github.com/Vouchflow/ios-sdk",
        from: "2.0.0" // use latest release tag
    )
]

Then add VouchflowSDK as a dependency of your target.

App Attest entitlement required Before calling enroll() or verify() on a physical device, add the App Attest capability to your app target. See App Attest setup below. Without it, the SDK will throw AttestationUnavailable and confidence will be capped at medium.

Initialisation

Call Vouchflow.configure(_:) once at app launch, before any call to verify(). The SDK is safe to configure in a background thread.

Use the write key, not the read key The SDK enrolls devices and starts verification sessions, both of which require write scope. Pass the write key (vsk_sandbox_… or vsk_live_…, no _read_ in the prefix) from Settings → API Keys. The read key is for server-side reputation lookups — using it here will return insufficient_scope on every call.
Swift — App entry point
import VouchflowSDK

@main struct MyApp: App {
  init() {
    try? Vouchflow.configure(VouchflowConfig(
      apiKey:       "vsk_sandbox_••••••••••••••••",  // write key, not read key
      environment: .sandbox   // .production in release builds
    ))
  }
}

VouchflowConfig parameters:

ParameterTypeRequiredDescription
apiKeyStringYesWrite-scoped key from Settings → API Keys. Look for the prefix vsk_sandbox_ or vsk_live_ (with no _read_). The read key will not work here.
environmentVouchflowEnvironmentNoDefaults to .production. Use .sandbox during development.
UIKit For UIKit apps, call Vouchflow.configure(_:) in application(_:didFinishLaunchingWithOptions:).

Enrollment

Enrollment is fully automatic — you never call it directly. On the first verify() call for a given device, the SDK:

  1. Generates an EC secp256r1 keypair in the Secure Enclave
  2. Obtains an App Attest assertion for the public key
  3. Registers the keypair with the Vouchflow backend (POST /v1/enroll)
  4. Stores the resulting device_token in the iOS keychain, marked kSecAttrAccessibleAfterFirstUnlock

Subsequent calls to verify() skip enrollment and go straight to the challenge-response flow. The SDK detects keychain loss (e.g. after device wipe) and re-enrolls automatically, producing a new device token.

Keychain persistence The device token is stored with kSecAttrSynchronizable = false so it does not sync to iCloud. If the app is deleted and reinstalled, the token is also deleted; re-enrollment produces a new token with no prior history, which is surfaced in the result as signals.keychainPersistent = false.

Checking enrollment status

If you need to know whether the device is already enrolled — without triggering a biometric prompt or network call — read cachedDeviceToken:

Swift
if let token = Vouchflow.shared.cachedDeviceToken {
  // Device is enrolled. token is the stable device identifier.
  // Safe to pass to your server for a reputation check before the user acts.
}

The property reads directly from Keychain and returns nil if:

  • The device has never completed enrollment
  • reset() was called
  • The Keychain is unavailable (e.g. device has never been unlocked since boot)

It is safe to call at cold start, on any thread, before the user authenticates. No biometric prompt or network request is made.

Verification

Call Vouchflow.shared.verify(context:) at any point where you need a device trust signal. The method is async/await and handles enrollment, biometric prompt, challenge signing, and result parsing internally.

Swift
do {
  let result = try await Vouchflow.shared.verify(
    context: .login  // .signup · .login · .sensitiveAction
  )

  // result.verified    — Bool
  // result.confidence  — .high / .medium / .low
  // result.deviceToken — opaque string; pass to your server if needed
  // result.signals     — VouchflowSignals (see below)
  proceedWithLogin()

} catch {
  handleVerificationError(error)
}

VouchflowResult fields:

FieldTypeDescription
verifiedBoolWhether the verification completed successfully.
confidenceConfidence.high, .medium, or .low.
deviceTokenStringStable opaque token for this device. Pass to your server to query reputation via GET /v1/device/{token}/reputation.
deviceAgeDaysIntDays since first enrollment.
networkVerificationsIntTotal verifications observed across the Vouchflow network for this device.
signals.keychainPersistentBooltrue if the device token survived an app reinstall.
signals.biometricUsedBooltrue if Face ID / Touch ID was presented.
signals.crossAppHistoryBooltrue if this device has verified in another Vouchflow-integrated app.
signals.attestationVerifiedBooltrue if App Attest assertion was validated by Apple.
signals.anomalyFlags[String]Active anomaly flags, if any (e.g. velocity_anomaly).
fallbackUsedBooltrue if email OTP fallback was used.

VerificationContext values:

ValueUse when
.signupNew account creation
.loginStandard authentication
.sensitiveActionHigh-value in-session actions (transfers, password change, etc.)

To require a minimum confidence level, pass minimumConfidence. If the device cannot meet it, the call throws VouchflowError.minimumConfidenceUnmet:

Swift — with minimum confidence
let result = try await Vouchflow.shared.verify(
  context:           .sensitiveAction,
  minimumConfidence: .high
)

Error handling

All errors thrown by verify() conform to VouchflowError. Handle the cases you care about; let others propagate or fall to a generic handler.

Swift — full error handling
do {
  let result = try await Vouchflow.shared.verify(context: .login)
  proceed(result)

} catch VouchflowError.biometricCancelled(let sessionId) {
  // User dismissed the biometric prompt. Offer retry.
  showRetryPrompt()

} catch VouchflowError.biometricFailed(let sessionId) {
  // Wrong biometric, lockout, or hardware error. Offer fallback.
  let fb = try await Vouchflow.shared.requestFallback(
    sessionId: sessionId,
    email: currentUser.email,
    reason: .biometricFailed
  )
  showOTPInput(expiresAt: fb.expiresAt)

} catch VouchflowError.biometricUnavailable {
  // No biometric enrolled or no hardware. Proceed to fallback directly.
  let fb = try await Vouchflow.shared.requestFallback(
    sessionId: currentSessionId,
    email: currentUser.email,
    reason: .biometricUnavailable
  )
  showOTPInput(expiresAt: fb.expiresAt)

} catch VouchflowError.minimumConfidenceUnmet {
  // Device cannot reach the required confidence threshold.
  showDeviceNotSupportedMessage()

} catch VouchflowError.networkUnavailable {
  // No internet. Surface a retry prompt.
  showOfflineError()

} catch {
  // Unexpected error — log and fail gracefully.
  logError(error)
  showGenericError()
}

All VouchflowError cases:

CaseDescriptionRecommended action
notConfiguredVouchflow.configure() was not calledFix at init — should not reach users
invalidApiKeyKey does not start with vsk_Fix at init
biometricUnavailableNo biometric enrolled or no hardwareOffer fallback
biometricCancelled(sessionId)User dismissed the promptOffer retry or cancel
biometricFailed(sessionId)Wrong biometric, lockout, or hardware errorOffer fallback
minimumConfidenceUnmetDevice cannot meet the requested thresholdBlock or degrade gracefully
enrollmentFailed(cause:)Enrollment failed; retried next callUsually transient; log it
attestationUnavailableApp Attest entitlement missing or device unsupportedConfidence capped at medium
sessionExpiredRepeatedlySession expired twice in a row (auto-retry failed)Show generic error, ask to retry later
networkUnavailableNo internet connectionSurface offline state
serverError(statusCode:code:message:)API returned a non-2xx responseLog; degrade gracefully

Fallback flow

When biometric fails or is unavailable, call requestFallback(sessionId:email:reason:) to trigger an email OTP. After the user enters the code, call submitFallbackOtp(sessionId:otp:).

Swift — OTP submission
let fbResult = try await Vouchflow.shared.submitFallbackOtp(
  sessionId: fallback.fallbackSessionId,
  otp: userEnteredCode
)
// fbResult.confidence is always .low
// fbResult.verified is true if OTP matched

App Attest setup

App Attest is required for confidence: .high in production. Without it, attestation is skipped and confidence is capped at .medium.

  1. Add the capability in Xcode
    Select your app target → Signing & Capabilities → click + → search for App Attest → add it. This adds the entitlement automatically.
  2. Verify the entitlement is present
    Open your .entitlements file and confirm com.apple.developer.devicecheck.appattest-environment is set to production for release builds and development for debug builds.
  3. Test on a physical device
    App Attest requires iOS 15+ and a physical device. On the simulator, the SDK skips attestation and returns confidence: .medium — this is correct behaviour in sandbox. In production builds, test on real hardware before shipping.
Entitlement file example
XML — MyApp.entitlements
<key>com.apple.developer.devicecheck.appattest-environment</key>
<string>production</string>
Match the entitlement value to the build channel Apple's appattest-environment entitlement only accepts development or production — these are Apple's own strings, not Vouchflow's sandbox/production. Map them like this: development for debug, simulator, and Vouchflow sandbox builds; production for App Store and TestFlight builds. Mismatching the value (e.g. production in a debug build) causes attestation to fail silently and confidence is capped at medium.
You must register your app's identity Set iosTeamId (your 10-character Apple Developer Team ID) and iosBundleId (your app's bundle identifier) in Settings → Account → App identity (attestation). App Attest assertions prove the key was minted on a real Apple device, but each assertion identifies the requesting app via <TEAM_ID>.<BUNDLE_ID> — the server has to match that against values you've registered. Without them, an attacker who pulled an attested key out of any other iOS app could submit it as if it came from yours. Until you register, all iOS devices fall back to confidence_ceiling: medium.
