Android SDK

Android SDK reference

The Android SDK integrates hardware-backed Keystore Attestation, hardware-backed key management, and biometric presentation into a single coroutine-based call. Requires Android API 28+ (Android 9). No Google Play Services dependency.

Installation

The SDK is distributed on Maven Central. No additional repository configuration or credentials are required.

build.gradle.kts (app)
dependencies {
  implementation("dev.vouchflow:android-sdk:latest.release")
}

Required manifest permissions (added automatically via manifest merger):

AndroidManifest.xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.USE_BIOMETRIC" />
<uses-permission android:name="android.permission.GET_ACCOUNTS" />
ProGuard / R8 The SDK ships with a bundled consumer ProGuard rules file. No additional configuration is needed.

Initialisation

Call Vouchflow.configure(VouchflowConfig(...)) once before any call to verify(). The best place is Application.onCreate().

Use the write key, not the read key The SDK enrolls devices and starts verification sessions, both of which require write scope. Pass the write key (vsk_sandbox_… or vsk_live_…, no _read_ in the prefix) from Settings → API Keys. The read key is for server-side reputation lookups — using it here will return insufficient_scope on every call.
Kotlin — Application class
import dev.vouchflow.sdk.Vouchflow
import dev.vouchflow.sdk.VouchflowConfig
import dev.vouchflow.sdk.VouchflowEnvironment

class MyApp : Application() {
  override fun onCreate() {
    super.onCreate()
    Vouchflow.configure(VouchflowConfig(
      apiKey      = "vsk_sandbox_••••••••••••••••",  // write key, not read key
      environment = VouchflowEnvironment.SANDBOX   // PRODUCTION in release
    ))
  }
}

VouchflowConfig parameters:

ParameterTypeRequiredDescription
apiKeyStringYesWrite-scoped key from Settings → API Keys. Look for the prefix vsk_sandbox_ or vsk_live_ (with no _read_). The read key will not work here.
environmentVouchflowEnvironmentNoPRODUCTION (default) or SANDBOX.
leafCertificatePinStringNoSHA-256 pin for the API leaf certificate. Rotates every 60 days.
intermediateCertificatePinStringNoSHA-256 pin for ISRG Root X1 (effectively permanent).
Certificate pinning in release builds Omitting the pin placeholders in release builds disables pinning entirely. We recommend supplying both pins in production and rotating leafCertificatePin before each Let's Encrypt renewal (every 60 days). See Going to production.

Enrollment

Like iOS, enrollment on Android is automatic. On the first verify() call, the SDK:

  1. Generates an EC secp256r1 keypair backed by StrongBox (if available) or TEE, with setAttestationChallenge(idempotencyKey)
  2. Reads the Keystore Attestation certificate chain via KeyStore.getCertificateChain() — this proves to Vouchflow's server that the key is in real hardware on a real Android device
  3. Registers the keypair with the Vouchflow backend (POST /v1/enroll) including the cert chain. The server walks the chain to the Google Hardware Attestation Root CA and verifies your app's package name and signing-cert SHA-256 against the values you registered in your Vouchflow account
  4. Stores the resulting device_token in Android AccountManager under the dev.vouchflow.sdk account type — this survives app uninstalls on most devices
AccountManager persistence Unlike the iOS keychain, AccountManager tokens can survive app uninstall on Android. The SDK queries for an existing account before enrolling. If an account is found from a previous install, the device token is reused and signals.persistentToken is true.

If hardware key attestation isn't supported (very old KeyMaster) or the chain doesn't validate (rooted device, manufacturer-specific issues), enrollment still succeeds but attestation_verified is false and confidence is capped at medium. VouchflowError.AttestationUnavailable is not thrown in this case; it is surfaced as a result signal.

You must register your app's identity Set androidPackageName (your applicationId from build.gradle) and androidSigningKeySha256 (the SHA-256 of your release signing certificate — run keytool -list -v -keystore release.jks, or copy it from Play Console → your app → Setup → App integrity → App signing) in the Android attestation section of your app's settings page. The Keystore Attestation chain proves the key was minted in real Android hardware, but the chain itself originates from some app — its leaf certificate carries that app's package name and signing-cert digest in the attestationApplicationId extension. Without your registered values, the server has nothing to match against, so a valid chain pulled from any other app would look just as legitimate as one from yours. Until you register, all Android devices fall back to confidence_ceiling: medium.

Verification

Call Vouchflow.shared.verify(activity, context). The activity parameter is required for the biometric prompt — pass the calling ComponentActivity.

Kotlin
import dev.vouchflow.sdk.*

// In a ViewModel or coroutine scope:
try {
  val result = Vouchflow.shared.verify(
    activity = requireActivity(),       // ComponentActivity
    context  = VerificationContext.LOGIN  // SIGNUP · LOGIN · SENSITIVE_ACTION
  )

  // result.verified            — Boolean
  // result.confidence          — Confidence.HIGH / MEDIUM / LOW
  // result.deviceToken         — opaque String
  // result.deviceAgeDays       — Int
  // result.networkVerifications — Int
  // result.signals             — VouchflowSignals
  proceedWithLogin()

} catch (e: VouchflowError) {
  handleError(e)
}

To require a minimum confidence level:

Kotlin — with minimum confidence
val result = Vouchflow.shared.verify(
  activity          = requireActivity(),
  context           = VerificationContext.SENSITIVE_ACTION,
  minimumConfidence = Confidence.HIGH
)

Payload signing

signPayload() produces a Vouchflow-attested JWS over any JSON-serializable payload — useful for mandate signing, transaction approval, or any scenario requiring a cryptographically verifiable signature tied to a specific device and biometric presentation.

The SDK canonicalizes the payload using RFC 8785 JCS before signing, ensuring byte-for-byte reproducibility regardless of JSON encoding. The default minimumConfidence is Confidence.HIGH — signing is high-assurance by default.

Kotlin — signPayload
val signed = Vouchflow.shared.signPayload(
  activity          = requireActivity(),
  context           = "mandate_signing",  // arbitrary, audited per session
  payload           = mapOf("v" to 1, "id" to "mand_abc", "scope" to "send"),
  minimumConfidence = Confidence.HIGH         // default
)

// signed.payload          — canonicalized JSON string the user actually signed
// signed.assertion        — Vouchflow-signed JWS your backend verifies
// signed.signature        — raw Keystore signature, base64 (rarely needed)
// signed.algorithm        — "ES256" (Keystore uses P-256)
// signed.deviceToken      — same opaque token as verify()
// signed.signingDeviceId  — sdv_… stable per-credential identifier
// signed.signedAt         — ISO 8601 timestamp
// signed.confidence       — "high" | "medium" | "low"
// signed.sessionId        — session_id for webhook correlation

// Send assertion to your backend for verification
val response = apiClient.post(
  path = "/api/mandates",
  body = mapOf("mandate" to signed.payload, "assertion" to signed.assertion)
)

Server-side verification. The assertion is a JWS signed by Vouchflow's verifier key. Your backend verifies it using jose against Vouchflow's JWKS endpoint — no Android-specific knowledge required:

TypeScript — Node.js backend
import { jwtVerify, createRemoteJWKSet } from 'jose'
import crypto from 'node:crypto'

const JWKS = createRemoteJWKSet(
  new URL('https://api.vouchflow.dev/.well-known/jwks.json')
)

// Verify the Vouchflow-signed JWS
const { payload } = await jwtVerify(assertion, JWKS, {
  issuer: 'https://vouchflow.dev',
  audience: YOUR_CUSTOMER_ID,
})

// Verify payload_sha256 matches your canonical payload
const expectedHash = crypto.createHash('sha256')
  .update(canonicalizedPayload)
  .digest('hex')

if (payload.payload_sha256 !== expectedHash) {
  throw new Error('Payload mismatch')
}

// payload.context          — "mandate_signing" from SDK call
// payload.confidence       — "high" | "medium" | "low"
// payload.signing_device_id— sdv_… stable credential identifier
// payload.device_token     — device's opaque token
When to use signPayload vs verify Use verify() for authentication and presence checks. Use signPayload() when you need a cryptographic signature over specific data (contracts, transaction details, approval records). The signed payload becomes a permanent audit record that can be verified independently of Vouchflow.

Error handling

All SDK errors are subclasses of VouchflowError (a sealed class). Handle the cases relevant to your UX; let others propagate to your global handler.

Kotlin — full error handling
try {
  val result = Vouchflow.shared.verify(requireActivity(), VerificationContext.LOGIN)
  proceed(result)

} catch (e: VouchflowError.BiometricCancelled) {
  showRetryPrompt()

} catch (e: VouchflowError.BiometricFailed) {
  val fb = Vouchflow.shared.requestFallback(
    email     = currentUser.email,
    reason    = FallbackReason.BIOMETRIC_FAILED
  )
  showOTPInput(fb.expiresAt)

} catch (e: VouchflowError.MinimumConfidenceUnmet) {
  showDeviceNotSupportedMessage()

} catch (e: VouchflowError.NetworkUnavailable) {
  showOfflineError()

} catch (e: VouchflowError) {
  logError(e)
  showGenericError()
}

InvalidApiKeyKey doesn't start with vsk_Fix at init
BiometricUnavailableNo biometric enrolled or no hardwareOffer fallback
BiometricCancelled(sessionId)User dismissed the promptOffer retry or cancel
BiometricFailed(sessionId)Wrong biometric, lockout, or hardware errorOffer fallback

OEM variance

Android's fragmented hardware ecosystem means biometric and attestation behaviour varies significantly across manufacturers. The SDK handles most variance internally, but the following are known issues worth being aware of.

OEM / DeviceIssueSDK behaviour
Samsung (Exynos chips)StrongBox may report availability but fail key generation under loadSDK falls back to TEE automatically; signals.attestationVerified may be false
Huawei (HMS devices)No Google Play Services, but Keystore Attestation works since it doesn't depend on PlayHardware attestation usually validates; falls back to medium only if the device's KeyMaster root isn't recognised
Xiaomi (MIUI)AccountManager access restricted in some MIUI versionsAccountStoreAccessDenied thrown; device token stored in shared preferences as fallback
VariousBiometric hardware reports enrolled but fails to promptBiometricFailed thrown after 3 consecutive failures; fallback offered
Android emulatorSoftware-only key generation; cert chain doesn't root in Google HW Attestation rootSandbox: shimmed to verified=true for dev convenience. Production: attestation_verified: false, capped at medium
Test on representative hardware We strongly recommend testing on at least one Samsung, one Pixel, and one Xiaomi device before going to production. The Android CTS does not guarantee consistent biometric or keystore behaviour across OEMs.
