Concepts

Core concepts

Vouchflow combines cryptographic device attestation, biometric proof, and cross-app history into a single trust signal. This page explains the model in depth so you can make good decisions about thresholds, fallback, and how Vouchflow fits into your risk stack.

Confidence levels

Every verification result includes a confidence field with one of three values. Confidence is a ceiling, not a score — it represents the highest trust level a session can support given all available signals. Each factor either preserves or lowers the ceiling; nothing raises it above what the hardware supports.

LevelWhat it meansTypical cause
high Cryptographic attestation verified by Apple or Google. Biometric presented. Secure Enclave or StrongBox key used. The strongest signal Vouchflow can produce. Normal operation on a modern iPhone or Play Protect–certified Android device with biometric enrolled.
medium Device is real and the key is hardware-backed, but attestation was not independently verified, or biometric was skipped by the user. Simulator build, OEM device without Play Services, user dismissed the biometric prompt.
low Cryptographic path could not complete. Email OTP fallback was used. The user proved access to an email address, not ownership of a specific device. No biometric enrolled on the device, Secure Enclave unavailable, repeated biometric failures triggering fallback.

What shifts confidence

The factors below are evaluated in order. Any factor that applies caps the confidence at that level — later factors cannot raise it back up.

FactorEffect on ceiling
Attestation verified by Apple or GoogleRequired for high. Without it, ceiling is medium.
Biometric acceptedRequired for high. Skipping biometric caps at medium.
Secure Enclave / StrongBox key confirmedStrongly correlated with high. Software-only keys cap at medium.
Active anomaly flag on deviceMay reduce by one level regardless of attestation result.
Email OTP fallback usedAlways results in low. Overrides all other factors.

Enforcing a minimum

Pass minimumConfidence when calling verify() to gate a flow on a specific level. If the device cannot meet the bar, the SDK throws MinimumConfidenceUnmet rather than returning a low-confidence result that your backend might not check.

Swift
// Gate a fund transfer on high confidence only
do {
    let result = try await Vouchflow.shared.verify(
        context: .sensitiveAction,
        minimumConfidence: .high
    )
    proceedWithTransfer(result)
} catch VouchflowError.minimumConfidenceUnmet {
    showStepUp()  // prompt user for an alternative second factor
}
Kotlin
try {
    val result = Vouchflow.verify(
        context = VerificationContext.SENSITIVE_ACTION,
        minimumConfidence = Confidence.HIGH
    )
    proceedWithTransfer(result)
} catch (e: MinimumConfidenceUnmetException) {
    showStepUp()
}
Set minimum confidence at the action level, not the app level. Use .high for fund transfers, password changes, and account-takeover recovery. Use .medium or omit it for standard logins. A blanket .high requirement blocks legitimate users on OEM Android devices that lack Play Protect certification, and users who have not enrolled biometric.

Acting on confidence

Confidence is an input to your risk decision, not the decision itself. The following is a starting point; tune based on your own chargeback and fraud rates.

ConfidenceRecommended response
high Proceed. A real device with a hardware-backed key that passed biometric. Treat it the same as a hardware security key second factor.
medium Proceed for standard actions. Consider reducing session lifetime, requiring step-up for high-value actions, and logging for pattern review.
low Apply additional friction for sensitive actions. Review fallbackUsed signals. Do not automatically block — fallback is a legitimate path for real users on constrained devices.

Device lifecycle

A device moves through a predictable lifecycle from first contact to potential retirement. Understanding this helps you interpret signals.keychainPersistent, deviceHasPriorVerifications, and anomaly flags correctly.

  1. First verification — automatic enrollment
    On the first call to verify(), the SDK generates an EC secp256r1 keypair in the Secure Enclave (iOS) or StrongBox/TEE (Android), obtains an attestation assertion from Apple or Google, and registers the device with Vouchflow via POST /v1/enroll. A device_token (prefixed dvt_) is returned and stored in the keychain or Android Keystore. The result contains signals.keychainPersistent = false because no prior token existed.
  2. Subsequent verifications
    The SDK retrieves the stored device_token, requests a fresh challenge from POST /v1/verify, signs it with the persisted Secure Enclave key, and submits the signature. No new keypair is generated. The result contains signals.keychainPersistent = true. The device accumulates history that feeds into the reputation score and network graph.
  3. App reinstall or keychain loss
    If the app is deleted and reinstalled, or the keychain is cleared (factory reset, MDM wipe), the stored device_token is lost. The next verify() call triggers re-enrollment and generates a new token. The new token has no prior history. The old token remains in Vouchflow's records but will never be used again. Call DELETE /v1/device/{token} to clean it up if you track tokens server-side.
  4. Device retirement
    To permanently remove a device from a user's account — on account deletion, user request, or confirmed fraud — call DELETE /v1/device/{device_token} with a read-scoped key. This removes the device record and all associated verification history. The action is immediate and irreversible.
New tokens are not inherently suspicious. App reinstalls are normal. A new device_token means the device has no prior history in your app, not that it is fraudulent. Look at the full picture: a new token with strong attestation and crossAppHistory: true is a very different signal from a new token with no attestation, a disposable email in the fallback path, and a velocity anomaly.

Device reputation

Each device tracked by Vouchflow accumulates a reputation profile. You can query it server-side with a read-scoped key — this is intended for risk evaluation at sign-in or before sensitive actions, not for inline verification (reputation is updated asynchronously).

HTTP
GET /v1/device/{device_token}/reputation
Authorization: Bearer vsk_live_read_••••••••••••••••••••

Risk score

The risk_score is an integer from 0 to 100. It is additive — each applicable factor contributes a fixed number of points. The score is recomputed asynchronously after each verification. Scores above 50 warrant additional scrutiny; above 80 indicate a high-risk device that should be blocked from sensitive actions.

FactorPointsInterpretation
Device age < 7 days+20Very new devices are statistically over-represented in fraud patterns.
Attestation never verified+15Without Apple/Google attestation, the hardware claim cannot be independently confirmed.
Single-app device, age < 30 days+10Devices seen in only one app with a short history lack cross-app corroboration.
Velocity anomaly (>5 enrollments / 7 days)+30Associated with device farms, test automation at scale, or credential-stuffing infrastructure.
Reinstall anomaly (>3 reinstalls / 30 days)+25Frequent reinstalls may indicate deliberate attempts to reset device history and evade reputation scoring.
Confidence degradation+20A device with a prior history of high confidence that now consistently returns low confidence. May indicate device transfer, hardware failure, or compromise.

Anomaly flags

The anomaly_flags array contains identifiers for active anomaly conditions. Flags are binary — present or absent. They are useful for building specific decision logic beyond the aggregate risk score.

FlagMeaningSuggested response
velocity_anomaly Unusually high enrollment rate across the Vouchflow network for this device fingerprint. Block enrollment from this device. Require human review before re-enabling.
reinstall_anomaly Frequent app reinstalls in a short window, consistent with deliberate history-clearing behaviour. Require a step-up verification (email confirmation, support contact) before re-enrolling.
confidence_degradation A device with a strong verification history is now consistently returning low confidence. Biometric may have been removed, or device may have changed hands. Trigger an account re-verification flow. Notify the account holder out-of-band.

Network graph

Device reputation improves with cross-app verification history. A device that has been seen across multiple Vouchflow-integrated apps carries stronger trust than one seen only once in a single app. The network graph aggregates those signals without sharing user identity between customers.

How it works

When a device verifies, Vouchflow records a network event keyed by SHA-256(public_key). This fingerprint is consistent across all customers that have seen the device, so aggregate counts accumulate over time. The raw public key is never shared between customers. The only cross-customer signals available are:

  • Total verification count across all apps on the network
  • Number of distinct customer apps that have seen the device
  • Platform (ios or android) and approximate device age
  • Whether attestation has ever been verified for this fingerprint, in any app

These are surfaced in the verification result as signals.networkVerifications (cumulative count) and signals.crossAppHistory (boolean — has the device verified in at least one other Vouchflow-integrated app).

Network participation is per customer account, not per device. Your account is either a network participant or it is not — you cannot selectively share specific devices. Non-participating customers still receive networkVerifications counts for their own app, but their devices do not contribute to or appear in cross-app signals for other customers. Participation is configured in your account settings.

Using network signals in decisions

Network signals are most useful as a trust booster for otherwise thin sessions — for example, a device re-enrolling after a reinstall. A device with networkVerifications > 50, crossAppHistory: true, and a risk_score below 20 has demonstrated consistent behaviour across the ecosystem and is very unlikely to be fraudulent even if its in-app history is short.

Privacy model

Vouchflow is designed to provide device trust signals without building user profiles. The data model reflects this constraint at every layer — Vouchflow knows about devices, not users.

What is stored

DataHow storedPurpose
Device public key SHA-256 fingerprint only — the key itself is discarded server-side after enrollment Cross-app deduplication in the network graph
Enrollment timestamp Exact UTC timestamp Device age calculation for the risk score
Verification outcome Confidence level and boolean flags per session Anomaly detection and reputation scoring
User email (fallback) Never stored — used only for OTP delivery and immediately discarded Delivers the OTP; not retained
Email hash (fallback) SHA-256 of submitted email Rate-limiting OTP requests per email address, not user identification
IP address (fallback) Held in memory for the duration of the OTP session, then discarded Verifies OTP was submitted from the same network as the initiation request
Biometric data Never transmitted or stored by Vouchflow Evaluated entirely on-device by the OS; only a pass/fail result reaches the SDK
Device model and OS version Platform string only (ios or android) — no model, OS version, or hardware identifiers OEM variance handling

Device tokens (dvt_…) are random identifiers. They carry no user identity on their own — they are opaque handles that let your backend correlate verifications from the same device without Vouchflow knowing which of your users owns it.

Data retention

Verification session records are retained for 90 days. Device records and reputation data persist until explicitly deleted. To remove a device and all associated history:

HTTP
DELETE /v1/device/{device_token}
Authorization: Bearer vsk_live_read_••••••••••••••••••••

Deletion is permanent and immediate. The device re-enrolls as new on next use, with no prior history.

GDPR and right to erasure. Because Vouchflow stores no user identity, a deletion request for a user maps to deleting the device tokens associated with that user in your own database, then calling DELETE /v1/device/{token} for each one. Maintain a mapping of user ID → device tokens server-side. See the GDPR compliance guide for a complete walkthrough.

Fallback handling

When a device cannot complete cryptographic verification — no biometric enrolled, repeated authentication failures, attestation unavailable — Vouchflow offers an email OTP fallback. Fallback always produces confidence: low. It is a deliberately degraded path, not an equivalent alternative to primary verification.

How fallback works

  1. Initiate fallback
    Call requestFallback(sessionId:email:reason:) (iOS) or requestFallback(sessionId, email, reason) (Android). The SDK sends the email address to Vouchflow, which delivers a 6-digit OTP and immediately discards the address. A SHA-256 hash of the email is retained only for rate-limiting.
  2. User enters OTP
    The OTP is valid for 5 minutes. Rate limits: 3 initiations per device per 24 hours, 5 per email hash per hour, 10 per IP per hour. After 5 incorrect entries the OTP is invalidated and the user must initiate fallback again.
  3. Submit and complete
    Call submitFallbackOtp(sessionId:otp:). On success the session completes and returns a result with confidence: .low, fallbackUsed: true, and a set of additional risk signals described below.

Fallback signals

A fallback result includes additional fields that give you context to make a better risk decision despite the lower confidence level:

FieldTypeWhat it tells you
ipConsistent Bool OTP was submitted from the same IP address as session initiation. Inconsistency may indicate OTP forwarding or a man-in-the-middle scenario.
disposableEmailDomain Bool The email domain is on a known disposable-provider list. Legitimate users rarely use throwaway email for account verification.
deviceHasPriorVerifications Bool This device token has previously completed primary-path (non-fallback) verifications. A device with prior history that suddenly needs fallback is much less suspicious than a brand-new device going straight to the fallback path.
otpAttempts Int Number of incorrect OTP entries before success. More than 1–2 attempts may indicate the code was shared, guessed, or intercepted rather than read directly from email.
timeToCompleteSeconds Int Seconds between OTP delivery and successful submission. Very fast completions (<10s) may indicate the OTP was pre-staged or auto-filled by an attacker.
Do not block users on fallback alone. A user with no biometric enrolled on an older phone is a real user. Combine fallback signals with your own account context before deciding to add friction. Only a combination of disposableEmailDomain: true, deviceHasPriorVerifications: false, a high risk_score, and otpAttempts > 2 justifies blocking outright.

API key types

Vouchflow issues four key types. Each has a distinct prefix, scope, and environment — never mix them up, and never embed a read or live key in a client application.

PrefixEnvironmentScopeUse it for
vsk_sandbox_ Sandbox Write SDK configuration during development. Authenticates POST /v1/enroll and POST /v1/verify in sandbox. Pass to the SDK in your app — sandbox keys have no effect in production and cannot be used to access real data.
vsk_sandbox_read_ Sandbox Read Server-side calls during development: GET /v1/device/{token}/reputation, DELETE /v1/device/{token}. Keep server-side only — do not embed in a client app.
vsk_live_ Production Write SDK configuration in production builds. Authenticates production enrollment and verification. Inject via CI/CD at build time — never commit to source control.
vsk_live_read_ Production Read Server-side calls in production: reputation queries, device deletion. Store in a server environment variable. Never expose in a client app or public repository.

Key rotation

When you rotate live keys in the dashboard, your existing keys are marked deprecated but remain valid for 14 days. During the overlap both old and new keys authenticate successfully. This gives deployed apps time to roll out an updated build before the old key stops working.

Vouchflow sends the Vouchflow-Key-Deprecated: true response header on any request authenticated with a deprecated key. If your server calls Vouchflow using the read key, watch for this header and update your environment variable before the 14-day window closes.

Sandbox keys cannot be rotated. Sandbox keys are fixed per account. If a sandbox key is compromised it can only be used to generate sandbox verifications, which have no effect on production data. Contact support if you need a sandbox key replaced.
